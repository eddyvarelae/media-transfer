Rung: **tested**. Rig: seat-unique disk images in the Dev scratchpad; the Tester's rig (`Ts*`) untouched. App = `file://` build, isolated userData, no hook unless named. Cards served read-only at 120 MB/s: `DevBCard` (the 213-file bench set) on :8769, `DevKCard` (A.JPG/a.JPG, two different DSC00001.JPG, X.JPG, two MP4s, BIG/, EMPTY/) on :8770.

## Root cause
exFAT on macOS reports a **synthetic negative inode** for a file while any handle on it is open and for about 5-10 ms after the last close; only then does the real (cluster-based) inode appear (`../K` probe output and the timing below). Empty files never get a real one (theirs stays synthetic, stable within a mount). 8cf1918 (H2) recorded a temp's identity through its write handle (and again after a re-open for set-times), so on exFAT it usually recorded the synthetic inode; the next check by path saw the real one -> "Temp replaced", the temp was failed, and its entry was dropped with the file left -> the next run called it foreign ("temp name taken by an unknown file"). Whether a given file failed depended on timing, which is why one run failed 211 and the next 212. My H2 harness evidence passed on exFAT by the same luck (two large files whose handle happened to show the real inode); the in-app full set did not run on exFAT. Timing measured with the app's write pattern: `0ms:-207 -> 7ms:28277` (six files, 5-7 ms each); a read handle opened right after close keeps the synthetic inode (`-213` through the handle and by path).

## Fix (`electron/noclobber.ts`, `electron/transfer.ts`)
- `noClobberProbe(destRoot)` per folder at run start: a probe file in `.media-transfer/` goes through exactly a temp's life (exclusive create, 1.5 MB write, close, set times through a handle, rename), stat'ed through the handle and by path after each step; removed afterwards (identity-checked). Profile: `handleStable` (no synthetic inode seen and handle == settled path, else false), `useBirth` (birthtime unchanged across set-times and rename), `removalEnabled` (settled dev + ino unchanged). The main log prints it per folder.
- Identity = dev + ino (+ birthtime only where `useBirth`). On handle-unstable volumes it is recorded by path after the close, once the inode settled (`lstatSettled`: waits in 5 ms steps while a non-empty file shows a negative inode), off the copy path; the read-back, `assertOwned` and every removal wait for that recording (`noClobberSettled`). Handle-vs-path re-checks (exFAT placeholder) use the handle only where `handleStable`. Where `removalEnabled` is false nothing is removed (kept, counted in tempsLeft).
- Behavior on exFAT that changed (documented in README): a temp left by a crash or unplug mid-copy has no recorded identity (the handle can't be trusted while open), so the next run leaves it alone and that file fails "temp name taken by an unknown file" until the user deletes it (`10-…` H2.1b exFAT). Cancel is unaffected (the seal records the identity after the close).
