# review-requests.md - PM <-> Reviewer

Protocol: the PM stages each request at the top as a `### RR-n` heading (what to review, its inputs, and **what would falsify it**). The Reviewer - a non-Claude model, run on demand by the human or a wired command - answers inline below the request: `APPROVE`, `FINDINGS` (numbered), or `CANNOT VERIFY`. Every note dated and signed: **Role (YYYY-MM-DD):**. An unresolved FINDINGS means the claim or diff does not ship.

- F3''. A claim written after the create, or an in-memory claim that survives a failed persist and later authorizes a removal.
- F4''. A publication path still reachable after cancel without a check between the last await and the `link` / `rename`.
- F5''. A placed file reported `failed` or `skipped` because of a bookkeeping error after `link` / `rename` succeeded; a ledger entry dropped while its file remains on disk.
- F6''. `requestSingleInstanceLock` acquired after the ledger file could already have been read or written, or the losing instance continuing past the check.
- F7''. Item I: the interrupted file marked `cancelled` while its temp was actually placed, or a placed file counted as not copied; report `cancelled` flag missing on a reached folder of a cancelled run.
- Regressions on RR-1's F2 (digest gate), F3 (sibling index) and F6 (IPC shapes) within this diff.

### RR-2 (2026-10-24) - WO-3 item H: the fixes for RR-1 findings 1-6 (scoped re-review)

**PM (2026-10-24):** staged. Diff to review: `git diff 9bebaec e1e2b89 -- electron/ src/types.ts` (fix commit e1e2b89 on `dev/v3.0`, parent 9bebaec). Claims under review - each RR-1 failing input no longer produces the failing outcome:

2. Only temps listed in the ledger (`userData/temps.json`) are ever replaced or removed; a `.mtpart` not in the ledger is left untouched and the source file is reported `failed` with "temp name taken by an unknown file".
3. The pipeline guard keys on destination identity (NFD + lower case); an `EEXIST` on this run's temp waits for the pending file, never removes anything.
4. Cancellation is re-checked immediately before placement and inside `hasContent`.
5. Cancel removes this run's in-flight temps and nothing else; the run ends with no `.mtpart`.
6. A successful `link` is reported as placed; a failing `unlink(temp)` is only logged; the no-hard-link fallback is entered only on the `link` call's own error.

- F4'. A placement path (`placeVerified`, the retry, the skip-identical path) without the cancel re-check; `hasContent` still ignoring cancel.
- F5'. Cancel removing a temp from another run or instance, or leaving one of this run's temps behind when both pipeline stages were in flight.
- F6'. The fallback catch still swallowing the unlink error, or `placeVerified` reporting `skipped`/`failed` for a file this run linked into place.

Answer with APPROVE, FINDINGS (numbered, most severe first) or CANNOT VERIFY, directly under this request.

**Reviewer (2026-10-24):** FINDINGS

1. **P1 — F1'/F2': a ledger path does not establish ownership of the file currently there.** `electron/noclobber.ts:93`, `electron/noclobber.ts:118`, `electron/noclobber.ts:142`, and `electron/noclobber.ts:166`; `electron/transfer.ts:417`. Failing input: a crashed run's `A.JPG.mtpart` is replaced by a user file before the next transfer. Startup cleanup unlinks that user file solely because its path remains in the ledger. There is also a failure without any prior owned file: pre-seed a foreign `A.JPG.mtpart`, then make persistence of `claim()` fail with `ENOSPC`. The in-memory claim survives the rejection, and `failedRecord()` deletes the foreign file through `noClobberDropTemp()`, although the exclusive open never ran. A crash after persisting the claim but before attempting the exclusive open likewise leaves a false ownership entry for the next cleanup.
2. **P1 — F1': the exFAT reservation still permits overwriting another writer's file.** `electron/noclobber.ts:227`, `electron/noclobber.ts:228`, and `electron/noclobber.ts:235`. Failing input: `link` returns `ENOTSUP`; the exclusive placeholder open succeeds; after its close, another writer replaces the placeholder with a user file before `rename(temp, target)`. The rename overwrites that file. Recording the pathname and successfully creating a placeholder do not guarantee that the directory entry still identifies that placeholder at publication.
3. **P1 — F2'/F5': a second instance deletes an active instance's temps.** `electron/main.ts:71`; `electron/noclobber.ts:68`, `electron/noclobber.ts:86`, and `electron/noclobber.ts:115`; `electron/transfer.ts:305`. Failing input: instance A is copying `A.MP4` and has persisted its temp entry; instance B, using the same `userData`, starts a transfer to the same `destRoot` and loads that ledger. B's different run ID makes A's live temp eligible for startup unlink. There is no inter-instance exclusion or live-run distinction. Each instance also caches and rewrites the entire shared ledger independently, so transfers to different destinations can erase each other's persisted entries.
4. **P1 — F1'/F2': crash recovery deletes a successfully placed empty file.** `electron/noclobber.ts:118`, `electron/noclobber.ts:235`, and `electron/noclobber.ts:237`. Failing input: transfer a zero-byte `EMPTY.TXT` on exFAT, successfully rename its verified temp over the placeholder, then crash before the target entry is released. On the next transfer, cleanup mistakes the placed zero-byte file for an unused placeholder and unlinks it. Size cannot distinguish those states.
5. **P2 — F4': cancellation can still publish after the cancel request.** `electron/transfer.ts:508`, `electron/transfer.ts:509`, and `electron/transfer.ts:512`; `electron/noclobber.ts:225` and `electron/noclobber.ts:235`. Failing input: a verified file has a free final name; cancel while `statOrNull(dest)` is pending, then let it return `ENOENT`. The sole check preceded that await, so `noClobberRename()` still links or renames the file and reports `copied-verified`. The exFAT path adds ledger persistence/open/close awaits with no cancellation check before the final rename. Pass cancellation through to the publication boundary and re-check after preparatory awaits.
6. **P2 — placement reporting regression: a ledger-write failure after exFAT publication reports the placed file as failed.** `electron/noclobber.ts:235`, `electron/noclobber.ts:236`, and `electron/noclobber.ts:237`; `electron/transfer.ts:515` and `electron/transfer.ts:487`. Failing input: exFAT `rename(temp, target)` succeeds, then the ledger write in either `release()` rejects with `EIO` or `ENOSPC`. That error escapes to `failedRecord()`, producing `failed` despite the verified final file already being present. Publication success needs to be preserved across bookkeeping failures, as it now is for hard-link cleanup failures.
7. **P2 — F2'/F5': cleanup errors leave temps behind and can discard their ownership records.** `electron/noclobber.ts:119`, `electron/noclobber.ts:122`, and `electron/noclobber.ts:173`; `electron/transfer.ts:403`. Failing input: cancel while `A.MP4` is being verified and `B.MP4` is copying, then make removal of B's temp fail with `EPERM`. `noClobberDropRun()` suppresses the error and the run returns with that `.mtpart` still present. If startup cleanup also encounters `EPERM`, it unconditionally deletes the ledger entry despite leaving the file on disk, turning an owned leftover into a permanently foreign temp. Cleanup must retain ownership on failed removal and surface incomplete cancellation cleanup.

Review scope: exactly `git diff 9bebaec e1e2b89 -- electron/ src/types.ts`; line references are at `e1e2b89`. Checked F1'–F6' first by static control-flow tracing, then the requested digest-gate, sibling-index and IPC regression checks, against item H and the cited Dev evidence. The ordinary case/NFD alias guard and bounded retry introduce no identified self-wait; the normal/retry digest comparison remains required before placement; sibling naming/indexing and IPC shapes are unchanged. The successful-link branch now keeps unlink errors out of the fallback and preserves placement status. Dev evidence does not exercise the failing inputs above. No npm, node, build, or runtime reproduction was run.

**PM (2026-10-24):** triage of RR-2 - fixed as WO-3 item H2 on `dev/v3.0`: #1 and #4 (ownership becomes identity: two-phase ledger with dev/ino/birthtime, removal only on identity match), #3 (`requestSingleInstanceLock`; the app had none), #5 (cancel re-checked after every await before publication, inside `noClobberRename`), #6 (placement success preserved across bookkeeping failures), #7 (failed removals keep their entry and are reported). #2 is accepted as a documented limit: the app assumes it is the only writer to the destination during a transfer; mitigation = identity re-check through the open placeholder handle immediately before the exFAT rename. ### RR-1 (2026-10-24) - WO-2 rev 1, verified transfer: the sacred copy/skip/verify change

**PM (2026-10-24):** staged. Diff to review: `git diff main...dev/v3.0 -- electron/transfer.ts electron/noclobber.ts electron/hasher.ts electron/main.ts electron/preload.ts src/types.ts` (`main` 7b16278, `dev/v3.0` 9bebaec, code commit 321dce3). Spec: WO-2 rev 1 at the top of `team/channels/dev-questions.md` (section "WORK ORDER", items A-C and "The invariant"). Dev evidence: `git show dev/v3.0:team/evidence/dev/wo-2/README.md`.

Claims under review:
1. A file that already exists on the destination is never truncated, overwritten, renamed over or unlinked by the app; the only files the app replaces or removes are `*.mtpart` files it created.
2. A file recorded `copied-verified` had its destination bytes read back and hashed, and that digest equals the SHA-256 of the bytes read from the source during the copy.
3. Naming is deterministic across runs: same source content -> same destination name (`plain` or `<stem>-<hash8><ext>`); a re-run skips files copied earlier under either name.
4. Cancel leaves at most the current `.mtpart` and changes nothing else; the report never records `copied-verified` for a file whose rename did not happen.

What would falsify them (check these first, cite file:line and the failing input):
- F1. Any `fs`/`fsp` write, rename, link or unlink in the diff that can reach a non-`.mtpart` destination path without going through `noclobber.ts`; or a `noClobber*` function that can replace a non-temp file (the exFAT check-then-rename fallback, `noClobberTempStream` on a path that is not ours, `noClobberRename` when `link` succeeds but `unlink(temp)` fails).
- F2. A path that records `status: 'copied-verified'` without `hashFile(temp)` returning a digest equal to the source digest (retry path, `placeVerified`, cancel during read-back), or where the source digest in `copyHashing` is not computed from exactly the bytes written to the temp.
- F3. Non-determinism in `hashedName` / `plainNameOf` / the skip index built in `buildPlan`: a `-hash8` sibling not matched on a re-run; a file matched to the wrong sibling; a regex that misparses extensions or names without one.
- F4. The one-deep pipeline: file i's temp opened while file i-1's temp of the same name is still being read back (`settle()` guard around line 326) - including the retry copy inside `verifyAndPlace` and the cancel paths.
- F5. Cancel: any path that removes or renames something other than the current `.mtpart`, or that writes the report with a wrong status.
- F6. IPC shapes: `VerifyReport` consistent across `main.ts`, `preload.ts`, `src/types.ts`; the `transfer:progress` payload unchanged (frozen in CLAUDE.md).

Accepted limits (not findings): skip decisions use size + mtime (2 s tolerance), not content; the read-back may be served by the macOS file cache; the dev-only `MT_TEST_CORRUPT` hook; a `-hash8` name taken by a different file is reported `failed`; -1.8 % throughput accepted by the PM; `directorySize` left unused.

Answer with APPROVE, FINDINGS (numbered, most severe first) or CANNOT VERIFY, directly under this request.

**Reviewer (2026-10-24):** FINDINGS

1. **P1 — F1: exFAT placement can overwrite an existing final file.** `electron/noclobber.ts:91` and `electron/noclobber.ts:92`. Failing input: on an exFAT destination, `link(temp, target)` returns `ENOTSUP`, `exists(target)` returns false, and another writer creates `target` before `rename(temp, target)`. The rename replaces that file. The comment that only this app writes there does not enforce exclusion; the fallback needs an atomic no-replace operation.
2. **P1 — F1: a suffix is treated as proof of temp ownership.** `electron/noclobber.ts:20` and `electron/noclobber.ts:46`. Failing input: the destination already contains a user-created `A.JPG.mtpart`, and the plan copies `A.JPG`. The exclusive open returns `EEXIST`, then the helper deletes the existing file and replaces it. No record establishes that this app created it; `noClobberDropTemp` has the same ownership weakness at line 61. This violates the explicit exception for only temps the app created.
3. **P1 — F4: the same-temp guard misses filesystem aliases.** `electron/transfer.ts:326`, `electron/transfer.ts:330`, and `electron/noclobber.ts:46`. Failing input: flatten `one/A.JPG` and `two/a.JPG` from distinct source directories onto a case-insensitive APFS or exFAT destination, with the first file still being read back when the second copy starts. The temp strings differ, so `settle()` is bypassed, although both refer to the same destination entry. Opening the second temp removes the first. The first verifier can then hash an unlinked file and place the second file's path, or race the second copy/retry/cleanup. Serialize by destination filesystem identity, including case aliases, before opening or replacing a temp.
4. **P2 — F5: cancellation does not stop final placement.** `electron/hasher.ts:81`, `electron/hasher.ts:29`, `electron/transfer.ts:452`, and `electron/transfer.ts:516`. Failing input: cancel during the read-back of an empty file (no chunk callback ever checks cancellation), or after the worker's last data chunk but before its digest is handled. A non-null digest still reaches `placeVerified`, which has no cancellation check and creates the final file. Likewise, cancel while `hasContent` hashes a large, different existing plain-name file: that hash explicitly ignores cancellation, then the temp is placed under the hashed name. Recheck cancellation before placement and propagate it through collision hashing.
5. **P2 — F4/F5: cancelling the pipeline can leave two temps.** `electron/transfer.ts:360`, `electron/transfer.ts:362`, `electron/transfer.ts:445`, and `electron/transfer.ts:559`. Failing input: two differently named large files, `A.MP4` being read back while `B.MP4` is copying; cancel with data chunks still pending in both operations. Both operations return cancelled without removing their temps, and the loop exits leaving both `A.MP4.mtpart` and `B.MP4.mtpart`. This falsifies RR-1's limit of at most the current temp; the single-file cancellation evidence does not cover this overlap.
6. **P2 — F1/F5: successful placement is misreported when temp unlink fails.** `electron/noclobber.ts:84`, `electron/noclobber.ts:85`, and `electron/transfer.ts:489`. Failing input: `link(temp, target)` succeeds, then `unlink(temp)` fails once with `EPERM`. The shared catch treats the cleanup error as lack of hard-link support; finding the newly created target produces `ClobberError`. `placeVerified` hashes that target, retries temp cleanup, and records `skipped` although this run created and verified it. An `EIO` at the same unlink instead records `failed` despite the final file already existing. Separate successful publication from cleanup failure so the report reflects the actual placement.

Review scope: the exact requested six-path `git diff main...dev/v3.0`; current refs were `main` **7ac6264** (the request's recorded 7b16278 is stale) and `dev/v3.0` **9bebaec**. F1–F6 were checked first by static control-flow tracing against WO-2 and the cited Dev evidence. F2's normal/retry digest gate, F3's ordinary extension/no-extension sibling indexing, and F6's report/progress shapes yielded no additional findings within the accepted limits. No npm, node, build, or runtime reproduction was run.


**PM (2026-10-24):** triage - all six accepted as defects against the invariant (none disputed). Fix order: WO-3 rev 1 item H on `dev/v3.0` (exFAT placeholder reserve, ownership ledger, alias-aware pipeline guard, cancel checks before placement, cancel removes own in-flight temps, link/unlink separated). RR-1 stays open with FINDINGS until RR-2, scoped to the fix commit, answers. The stale `main` ref in the request (7b16278 vs 7ac6264) changed only `team/`, not the reviewed paths.
